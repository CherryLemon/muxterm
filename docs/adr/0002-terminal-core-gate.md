# ADR 0002: terminal-core capability gate (not yet passed)

* Status: **passed** — `alacritty_terminal` 0.26 is adopted; the evidence is in
  `docs/adr/0004-terminal-core-choice.md`, `crates/term-core/tests/gate.rs` and
  `poc core-gate`
* Date: recorded with the first PoC commit
* Provenance: our own design decision; the candidate crates are third-party,
  their licences are recorded in `docs/licences.md`.

## Context

The project needs a terminal emulator (grid, scrollback, selection, control-sequence
state) that can be **reconstructed from a snapshot** rather than only fed a live
stream. "It runs a shell" is not the requirement.

## Gate: what a candidate must demonstrate

A candidate is adopted only if all of these hold, each with a test in this
repository:

1. **Restore from `capture-pane` output.** Feed a captured screen (with the escape
   sequences tmux emits under `-e`) and reach a grid identical to the pane's real
   screen, including styled cells and wide characters.
2. **State, not only text.** Cursor position, alternate screen, scroll region,
   history size and wrapping state can be set from information obtained outside the
   byte stream (the per-pane metadata queries), not only by replaying the original
   sequences.
3. **Side-effect isolation.** Terminal responses generated by the emulator (device
   status reports, cursor position reports, DA responses) can be suppressed or
   captured instead of being written back to the pane. During history restoration
   nothing may ring a bell, touch the clipboard, raise a notification or answer a
   query.
4. **Read-only export for rendering.** A renderer can read cells, attributes and
   selection geometry without taking a lock that blocks input, and without the
   emulator owning any window or GPU state.
5. **Bounded memory.** A configurable scrollback budget that is actually enforced.

If a candidate satisfies 1–3 but not 4, a *bounded* adapter patch is acceptable;
forking the world is not.

## Explicitly rejected approaches

* Building a terminal emulator from `vte` alone: that turns the project into a
  terminal-compatibility effort and away from the tmux integration that is its
  point.
* Treating a tmux pane's whole TUI output as screen content and rendering it as an
  ordinary text view: it cannot express tabs/splits as native GUI objects, which is
  the entire product idea.

## Result

All five points were demonstrated, four of them twice: once with synthetic captures
(`crates/term-core/tests/gate.rs`) and once against a real tmux 3.4 pane
(`poc core-gate`, which compares the restored grid with a second, independent
`capture-pane` of the same pane and with the cursor/alternate/history values tmux
reports).

Two things the gate surfaced are recorded as limitations rather than fixed:
the wrap flag of a joined logical line is not restored, and per-pane application
modes (bracketed paste, application cursor keys) still cannot be recovered from a
snapshot.  See `docs/spec/state-sync.md` §5.

## Consequence

The snapshot stays a project-owned data type (`ScreenSnapshot`) and the GUI depends
on `term_core::TerminalCore`, never on the emulator.  The reconnect scenario
continues to check the data-level contract, which is what made it possible to adopt
a core afterwards without rewriting it.
